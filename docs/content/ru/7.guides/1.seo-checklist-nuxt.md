Большинство SEO-регрессий в Nuxt-приложении это не проблемы стратегии, а проблемы кода: `noindex`, переживший релиз, canonical, собранный от неправильного базового URL, дерево заголовков с пропущенным уровнем, sitemap, в котором всё ещё лежит удалённый роут. Этот чеклист проходит по двенадцати областям, которые Google Search Central описывает как технические требования, показывает код на Nuxt 4 для каждой из них и называет правила ranklint, которые валят сборку, когда код уезжает. У Яндекса набор требований почти тот же, но отчёты и подтверждение прав живут в Яндекс.Вебмастере, а не в Search Console, и расхождения отмечены прямо в соответствующих блоках.

Все сниппеты ниже используют API, которые поставляются с Nuxt 4, `@nuxtjs/i18n`, `@nuxt/image`, `@nuxtjs/robots` или самим модулем `@ranklint/nuxt`. Идентификаторы правил ведут в полный справочник: [Все правила](/ru/rules).

## Индексируемость

Индексируемая страница обязана одинаково отвечать на три вопроса: что говорит мета-тег robots, что говорит заголовок `X-Robots-Tag` и что разрешает robots.txt. Google Search Central прямо пишет, что закрытую в robots.txt страницу прочитать нельзя, поэтому `noindex` внутри неё никто не увидит, а URL всё равно может попасть в выдачу без сниппета. Яндекс читает те же директивы, но дополнительно учитывает `Clean-param`, которая схлопывает дубли по параметрам запроса и которую Googlebot игнорирует, так что в общем robots.txt её стоит держать отдельно от правил обхода, важных для Google.

Вторая половина индексируемости это серверный рендеринг. Если основной контент появляется только после гидратации, первый проход краулера видит пустую оболочку. В Nuxt это обычно означает страницу с `ssr: false` или загрузку данных в `onMounted` вместо `useAsyncData`.

```ts
// app/pages/admin/[id].vue
useHead({
  meta: [{ name: 'robots', content: 'noindex, follow' }],
})

// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['@nuxtjs/robots', '@ranklint/nuxt'],
  robots: {
    disallow: ['/admin', '/checkout'],
    sitemap: ['https://example.com/sitemap.xml'],
  },
  ranklint: {
    site: { url: 'https://example.com', name: 'Example' },
    robots: { mode: 'external' },
  },
})
```

Владеть `/robots.txt` может только один модуль. Если в стеке есть `@nuxtjs/robots`, файл пишет он, поэтому `@ranklint/nuxt` запускается с `robots: { mode: 'external' }` (или `robots: false`) и не регистрирует конкурирующий обработчик роута. Обратный вариант тоже рабочий: выкинуть `@nuxtjs/robots`, оставить дефолтный `mode: 'owner'`, и модуль ranklint отдаст robots.txt с учётом окружения, закрыв непродакшн-хосты и объявив sitemap.

## Canonical и дубли

Google считает `rel=canonical` сильной подсказкой, а не командой, и при расхождении сигналов выбирает канонический URL сам. Практическое правило из Search Central: каждая индексируемая страница объявляет абсолютный canonical на саму себя, а дубли указывают на ту версию, которую вы действительно хотите видеть в выдаче. Яндекс реагирует на тот же тег, но сходится медленнее, и на больших каталогах стабильный canonical от этого только ценнее.

В Nuxt-проектах доминируют два сценария поломки. Первый это относительный canonical без origin, собранный из одного `useRoute().fullPath`. Второй это цепочка: страница A указывает на B, B указывает на C. Собирайте значение из `useRequestURL()`, тогда origin будет корректным и на localhost, и на превью-деплоях, и в продакшене.

```ts
// app/pages/products/[slug].vue
const url = useRequestURL()
const canonical = `${url.origin}${url.pathname}`

useHead({
  link: [{ rel: 'canonical', href: canonical }],
})
```

## Title и description

Search Central просит уникальный описательный `<title>` на каждую страницу и мета-описание, которое пересказывает страницу, а не повторяет заголовок. Ни то, ни другое само по себе не рычаг ранжирования, но оба управляют сниппетом, а отсутствие описания означает, что Google напишет его сам из тела страницы. Open Graph и Twitter-теги вообще не поисковые сигналы, они решают, как расшаренная ссылка выглядит в мессенджерах и соцсетях, и поэтому живут в том же блоке кода.

`useSeoMeta` это плоский типизированный способ описать всё это в Nuxt 4. Держите title в районе 30-60 символов, а description в районе 70-160: именно такие дефолты у ranklint.

```ts
// app/pages/products/[slug].vue
const route = useRoute()
const { data: product } = await useAsyncData(() => $fetch(`/api/products/${route.params.slug}`))

useSeoMeta({
  title: () => `${product.value.name} price and specs`,
  description: () => product.value.summary,
  ogTitle: () => product.value.name,
  ogDescription: () => product.value.summary,
  ogImage: () => product.value.image,
  ogType: 'website',
  twitterCard: 'summary_large_image',
})
```

## Заголовки

Google Search Central описывает заголовки как способ выразить структуру документа, а не как инструмент оформления. Один `h1` на страницу, без пропуска уровней, без пустых заголовков, оставленных компонентом, который рендерит слот с названием по условию. Скринридеры читают то же дерево, так что выигрыш в доступности достаётся бесплатно.

Специфичная для Nuxt ловушка это лейауты. Лейаут, который рендерит имя сайта внутри `h1`, плюс страница со своим `h1` дают два заголовка первого уровня на каждом роуте и одинаковый текст `h1` по всему сайту. Оставьте в лейауте `div` или `p`, а единственный `h1` отдайте странице.

```vue
<!-- app/pages/products/[slug].vue -->
<template>
  <article>
    <h1>{{ product.name }}</h1>
    <h2>Specifications</h2>
    <h3>Dimensions</h3>
    <h2>Reviews</h2>
  </article>
</template>
```

## hreflang и i18n

Документация по hreflang на Search Central формулирует одно жёсткое требование: аннотации должны быть взаимными. Если английская страница перечисляет немецкую, немецкая обязана перечислить английскую в ответ, и в каждом наборе должен быть `x-default` для языкового переключателя или запасной локали. Нарушенная взаимность молча игнорируется, поэтому теги выглядят проставленными в исходнике страницы и при этом ничего не делают. Яндекс эти же аннотации читает и использует их для выбора языковой версии.

В Nuxt `@nuxtjs/i18n` генерирует весь набор из конфига локалей, если у каждой локали есть тег `language` в формате BCP 47, а `baseUrl` абсолютный. Композабл возвращает ref, поэтому передавайте его в `useHead` геттером: одно разворачивание `.value` в setup заморозит аннотации на первом отрендеренном роуте.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['@nuxtjs/i18n'],
  i18n: {
    baseUrl: 'https://example.com',
    defaultLocale: 'en',
    strategy: 'prefix_except_default',
    locales: [
      { code: 'en', language: 'en-US' },
      { code: 'de', language: 'de-DE' },
    ],
  },
})
```

```ts
// app/app.vue
const head = useLocaleHead({ seo: true })

useHead(() => ({
  htmlAttrs: head.value.htmlAttrs,
  link: head.value.link,
  meta: head.value.meta,
}))
```

- [`hreflang:valid-targets`](/ru/rules/i18n/hreflang-valid-targets)
- [`i18n:no-locale-leak`](/ru/rules/i18n/i18n-no-locale-leak)

## JSON-LD

Расширенным сниппетам нужна структурированная разметка, и Search Central предпочитает JSON-LD микроданным, потому что он не переплетается с вёрсткой. Яндекс читает JSON-LD наравне с Google и строит по нему свои расширенные сниппеты. Ломаются в продакшене обычно две тривиальные вещи: JSON не парсится, чаще всего после того как в скрипт подставили строку с неэкранированной кавычкой, либо у выбранного типа не хватает обязательного свойства, и тогда тип отбрасывается целиком, а не понижается.

Модуль `@ranklint/nuxt` поставляет `useJsonLd(type, data)`, который рендерит скрипт через `useHead` с проставленными `@context` и `@type` и валидирует полезную нагрузку через Zod только в dev. Без модуля эквивалент это обычный `useHead` с сырым скриптом.

```ts
// app/pages/products/[slug].vue
useJsonLd('Product', {
  name: product.value.name,
  description: product.value.summary,
  offers: { price: product.value.price, priceCurrency: 'EUR' },
})

// without the module
useHead({
  script: [{
    type: 'application/ld+json',
    innerHTML: JSON.stringify({
      '@context': 'https://schema.org',
      '@type': 'Organization',
      name: 'Example',
      url: 'https://example.com',
    }),
  }],
})
```

### Как это проверяет ranklint

- [`jsonld:parseable`](/ru/rules/structured-data/jsonld-parseable)
- [`jsonld:valid-schema`](/ru/rules/structured-data/jsonld-valid-schema)

## Хлебные крошки

Расширенный сниппет с хлебными крошками заменяет сырой URL в результате Google на читаемый путь, и Search Central требует тип `BreadcrumbList` с упорядоченным `itemListElement`, где у каждого элемента есть `position`, `name` и `item`. Яндекс рисует свою навигационную цепочку по той же разметке. Список обязан повторять то, что видит пользователь: невидимые крошки, существующие только в JSON-LD, это нарушение правил структурированных данных.

Рендерьте видимую цепочку через `NuxtLink`, чтобы внутренняя навигация оставалась клиентской, а краулер всё равно получал настоящие `href`, и отдавайте соответствующий JSON-LD из того же массива.

```vue
<!-- app/components/Breadcrumbs.vue -->
<script setup lang="ts">
const props = defineProps<{ product: { name: string, slug: string } }>()

const crumbs = [
  { name: 'Home', path: '/' },
  { name: 'Products', path: '/products' },
  { name: props.product.name, path: `/products/${props.product.slug}` },
]

useJsonLd('BreadcrumbList', {
  itemListElement: crumbs.map((crumb, index) => ({
    '@type': 'ListItem',
    position: index + 1,
    name: crumb.name,
    item: `https://example.com${crumb.path}`,
  })),
})
</script>

<template>
  <nav aria-label="Breadcrumb">
    <NuxtLink v-for="crumb in crumbs" :key="crumb.path" :to="crumb.path">
      {{ crumb.name }}
    </NuxtLink>
  </nav>
</template>
```

### Как это проверяет ranklint

- [`jsonld:valid-schema`](/ru/rules/structured-data/jsonld-valid-schema)
- [`jsonld:parseable`](/ru/rules/structured-data/jsonld-parseable)
- [`links:no-broken`](/ru/rules/links/links-no-broken)

## Sitemap

Sitemap это помощь в обнаружении, а не гарантия индексации. Search Central ясно говорит, что в нём должно лежать: только канонические, индексируемые URL, отвечающие 200. Страница с `noindex` в sitemap это противоречивый сигнал, а 404 в sitemap тратит краулинговый бюджет на каждом запросе. Сам файл обязан быть объявлен в robots.txt директивой `Sitemap:`, и именно так его находит Яндекс, когда хост не подтверждён в панели вебмастера. Директива `Host` в том же robots.txt давно устарела и Яндексом не учитывается, главное зеркало определяется редиректами и canonical.

Модуль `@ranklint/nuxt` отдаёт `/sitemap.xml` без всякой конфигурации: собирает статические роуты из `app/pages`, приводит каждый `loc` к абсолютному виду относительно `site.url` и экранирует XML. Динамические роуты приходят из явных источников.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['@ranklint/nuxt'],
  ranklint: {
    site: { url: 'https://example.com', name: 'Example' },
    sitemap: {
      path: '/sitemap.xml',
      autoRoutes: true,
      cacheTtl: 3600,
      sources: [
        '/api/seo/product-urls',
        { loc: '/pricing', changefreq: 'weekly', priority: 0.8 },
      ],
    },
  },
})
```

### Как это проверяет ranklint

- [`sitemap:reachable`](/ru/rules/indexability/sitemap-reachable)
- [`sitemap:no-noindex`](/ru/rules/indexability/sitemap-no-noindex)
- [`robots:sitemap-declared`](/ru/rules/robots/robots-sitemap-declared)
- [`robots:reachable`](/ru/rules/robots/robots-reachable)
- [`links:no-orphans`](/ru/rules/links/links-no-orphans)

## Изображения

Документация Google Картинок просит описательный `alt` у смысловых изображений и пустой `alt` у декоративных. Стабильность вёрстки важна не меньше: собственные `width` и `height` позволяют браузеру зарезервировать место, это удерживает Cumulative Layout Shift низким, а CLS входит в Core Web Vitals.

Третье правило про `loading="lazy"`. Ленивая загрузка ниже первого экрана это выигрыш, ленивая загрузка героя откладывает Largest Contentful Paint на каждом визите. `NuxtImg` не добавляет `loading` сам, это обычный атрибут, пробрасываемый в `img`, поэтому ставьте `loading="lazy"` явно на картинки ниже первого экрана, а герою вместо этого проставляйте проп `preload`.

```vue
<template>
  <NuxtImg
    src="/img/hero.jpg"
    alt="Blue widget on a workbench"
    width="1200"
    height="630"
    sizes="100vw md:1200px"
    format="webp"
    preload
  />
  <NuxtImg src="/img/gallery-1.jpg" alt="Widget from the side" width="600" height="400" loading="lazy" />
</template>
```

### Как это проверяет ranklint

- [`images:alt-required`](/ru/rules/images/images-alt-required)
- [`images:dimensions-required`](/ru/rules/images/images-dimensions-required)
- [`images:no-lazy-above-fold`](/ru/rules/images/images-no-lazy-above-fold)

## Внутренние ссылки

Search Central описывает краулинг как обнаружение по ссылкам: страница, на которую никто не ссылается, находится только через sitemap, и её важность считывается как низкая. Внутренним ссылкам нужен настоящий `href` в серверном HTML, и `NuxtLink` его выдаёт, в отличие от `div` с обработчиком `@click`, который навигирует программно.

Вторая половина это консистентность. Выберите одно соглашение по завершающему слешу на весь сайт и держите на нём каждую внутреннюю ссылку, иначе каждый роут существует как два URL и сигналы делятся пополам. По-настоящему внешние ссылки помечайте `external`, чтобы Nuxt не пытался разрешить их через роутер.

```vue
<template>
  <NuxtLink to="/products/blue-widget">Blue widget</NuxtLink>
  <NuxtLink to="https://status.example.com" external target="_blank" rel="noopener">
    Status page
  </NuxtLink>
</template>
```

### Как это проверяет ranklint

- [`links:no-broken`](/ru/rules/links/links-no-broken)
- [`links:trailing-slash-consistent`](/ru/rules/links/links-trailing-slash-consistent)
- [`links:no-orphans`](/ru/rules/links/links-no-orphans)

## HTTP и редиректы

Переехавший URL получает 301, и Search Central утверждает, что постоянный редирект это самый сильный сигнал склейки из существующих, тогда как 302 говорит краулеру сохранить старый URL. Вторая проблема это цепочки: каждый лишний переход стоит краулингового бюджета и размывает сигнал, поэтому редиректьте сразу на конечный адрес, а не через два промежуточных роута. Яндекс следует тем же правилам, но склеивает 301 медленнее, часто за несколько циклов обхода.

Остальная часть этого блока это гигиена, которая видна только в ответе: смешанный контент на HTTPS-странице, удалённый товар, который отдаёт 200 с пустым телом вместо 404, мета-тег viewport, отсутствующий при mobile-first индексации, и время до первого байта, которое растёт, пока не падает скорость обхода.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/old-pricing': { redirect: { to: '/pricing', statusCode: 301 } },
    '/blog/**': { swr: 3600 },
  },
  app: {
    head: {
      meta: [{ name: 'viewport', content: 'width=device-width, initial-scale=1' }],
    },
  },
})
```

### Как это проверяет ranklint

- [`links:permanent-redirects`](/ru/rules/links/links-permanent-redirects)
- [`links:no-redirect-chain`](/ru/rules/links/links-no-redirect-chain)
- [`http:no-mixed-content`](/ru/rules/http/http-no-mixed-content)
- [`http:no-soft-404`](/ru/rules/http/http-no-soft-404)

## Запуск локально и в CI

Всё вышеперечисленное проверяемо до деплоя. Запустите приложение, направьте на него ranklint, и краулер обойдёт сайт, прогонит все 42 правила и выйдет с кодом 1, когда найдётся проблема уровня error. Без конфига аудит идёт по минимальному конфигу, выведенному из origin переданного URL, и для первого прохода этого достаточно.

```bash
npm run dev
npx ranklint audit --url http://localhost:3000
```

```bash
npx ranklint audit --url https://example.com --reporter markdown --json-output report.json
```

В пайплайне полезная связка это аудит плюс diff: аудит валит джобу на новых error-проблемах, а diff сравнивает текущий отчёт с отчётом базовой ветки, чтобы в ревью было видно только то, что сломало это изменение. Настройка для GitHub Actions и GitLab CI, включая закреплённый комментарий в пулл-реквесте и загрузку SARIF, лежит в [Diff и CI](/ru/cli/diff-and-ci).
